# Internationalization

How Wizda decides which language to show, and the checklists for changing anything about it. For the *backend* side of localization — how `nameJa`/`nameKo`/`nameDe` get scraped and aligned — see [`docs/domain.md`](./domain.md)'s "Localized names". For agreed in-game wording per language see [`docs/glossary.md`](./glossary.md).

## The rule

**The URL path is the single source of truth for language.** Every page lives under a locale segment:

```
/en            /ja              home (the Junk Oracle)
/en/junks      /ja/junks        junk list
/en/equipment  /ja/equipment    equipment list
/en/about      /ja/about        about
```

Both locales are statically prerendered at build time (`generateStaticParams` in [`app/[lang]/layout.tsx`](../packages/web-client/src/app/%5Blang%5D/layout.tsx)), so the HTML that arrives is *already* in the right language — `<html lang>`, every label, and every one of Wizda's lines. Nothing about the language is decided in the browser.

That is the whole point. The previous design kept the preference in `localStorage` and applied it in a post-mount effect, which meant the prerendered English painted first and swapped to Japanese once the JS had loaded. No amount of client-side tuning could fix that: the English was in the bytes before any script ran. Moving the language into the URL is what removed the flash.

### What resolves a language-less URL

`/`, `/junks` and friends name no language, so [`middleware.ts`](../packages/web-client/src/middleware.ts) redirects them, resolving in this order:

1. the `wizda.lang` cookie — an explicit past choice,
2. the `Accept-Language` header,
3. English.

This mirrors the precedence in [`backend-api/src/locale.ts`](../packages/backend-api/src/locale.ts), minus the `?lang=` step (the path plays that role here).

**A prefixed URL is never redirected.** `/ja/junks` shows Japanese even if the cookie says `en`. If the cookie could override the path, sharing a `/ja/` link would be broken — the recipient would get their own language and the URL would be lying about its contents. The cookie only ever answers URLs that name no language.

### The cookie

`wizda.lang`, one value (`en` or `ja`), one year, `SameSite=Lax`, written **only by a click on the language switcher** — auto-detection never writes it. A visitor who never touches the switcher stores nothing at all. It is consent-exempt (a UI preference the user explicitly asked for) which is why there is still no consent banner; see [`docs/analytics.md`](./analytics.md)'s "The one cookie, and why it needs no banner".

## Where a language lives

Four files carry a language's *text*. Maintaining Japanese — a rewording, a native editor's pass, a term the game renamed — means these and nothing else:

| File | Holds |
| --- | --- |
| [`i18n/strings.<lang>.ts`](../packages/web-client/src/i18n/strings.ja.ts) | every UI-chrome label, `<title>`/`<description>`, and the vocab tables (grade colours, rank names, category and equipment-type names, blessing stat labels) |
| [`mascot/voice.<lang>.ts`](../packages/web-client/src/mascot/voice.ja.ts) | Wizda's lines only — greetings, help text, snark, confirmations |
| [`i18n/glossary.<lang>.ts`](../packages/web-client/src/i18n/glossary.ja.ts) | the shared core nouns (`JA_EQUIPMENT`, `JA_GRADE`, …) that *both* catalogs above interpolate, so one concept is never named two ways. **EN has no such file** — it needs no enforced consistency and its terms are the type names themselves |
| [`docs/glossary.md`](./glossary.md) | the agreed in-game wording per language, and how each term was confirmed. Change a term here and in `glossary.<lang>.ts` together |

Retermings are why the glossary indirection exists: swapping 追加護 for another word is one edit in `glossary.ja.ts`, not a search across two catalogs.

Everything else is **language-agnostic machinery** — it reads `OFFERED_LANGUAGES` or a catalog and needs no edit when a language's wording changes:

- [`i18n/locale.ts`](../packages/web-client/src/i18n/locale.ts) — the offered set, endonyms, `localeHref`, `stripLocale`. A deliberate leaf module (see Gotchas).
- [`i18n/languageStore.ts`](../packages/web-client/src/i18n/languageStore.ts) — the two registries mapping a language to its catalogs, plus the module-level mirror non-React modules read.
- [`i18n/LanguageProvider.tsx`](../packages/web-client/src/i18n/LanguageProvider.tsx), [`middleware.ts`](../packages/web-client/src/middleware.ts), [`app/[lang]/layout.tsx`](../packages/web-client/src/app/%5Blang%5D/layout.tsx), [`app/pageMetadata.ts`](../packages/web-client/src/app/pageMetadata.ts), [`app/sitemap.ts`](../packages/web-client/src/app/sitemap.ts), [`components/LanguageToggle.tsx`](../packages/web-client/src/components/LanguageToggle.tsx).
- Tests: `i18n/strings.test.ts` and `mascot/voice.test.ts` enforce structural parity and non-empty leaves across every catalog; `i18n/locale.test.ts` covers resolution. A wording change should never need a test edit — if it does, the test was asserting content it shouldn't.

**Item names are not in any catalog.** Equipment and junk names come from the API as `displayName`/`junkDisplayName`, resolved server-side from the scraped `nameJa`/`nameKo`/`nameDe` columns. Fixing a wrong *item* name is a backend/seed job — [`backend-api/src/locale.ts`](../packages/backend-api/src/locale.ts), `src/localizedNames.ts`, and `prisma/seed-from-html/seedLocalizedNames.ts` + `alignLocalizedNames.ts` — see [`docs/domain.md`](./domain.md)'s "Localized names". Japanese search readings (`nameReading`) come from the same seed's `seedJapaneseReadings.ts`; see [`docs/search.md`](./search.md).

**Two surfaces are English-only on purpose.** `app.constants.ts`'s `APP_DESCRIPTION` and the PWA manifest ([`app/manifest.ts`](../packages/web-client/src/app/manifest.ts)) have no locale to resolve against — the manifest is fetched once, outside any `[lang]` route. `ORACLE_NAME` is untranslated for a different reason (see Gotchas).

## Adding a language

Everything is driven off `OFFERED_LANGUAGES`, so the order matters less than the completeness. In [`i18n/locale.ts`](../packages/web-client/src/i18n/locale.ts) and [`i18n/languageStore.ts`](../packages/web-client/src/i18n/languageStore.ts):

1. **`SupportedLanguage`** — widen the `Extract<LanguageCode, …>` union. The backend's `LanguageCode` already knows `ko` and `de`; they're deliberately *not* offered because they have no UI catalog yet.
2. **`OFFERED_LANGUAGES`** and **`LANGUAGE_ENDONYMS`** — add the code and the language's own name for itself (never translated).
3. **`i18n/glossary.<lang>.ts`** — the language's core nouns, if it needs the consistency (see "Where a language lives"). Settle these *first*: both catalogs below interpolate them.
4. **`strings.<lang>.ts`** — a parallel of `strings.en.ts`, `satisfies UiStrings`. A missing entry is a compile error, and `strings.test.ts` fails on a blank one or a shape mismatch.
5. **`mascot/voice.<lang>.ts`** — Wizda's own catalog, same deal. See [`docs/wizda-voice.md`](./wizda-voice.md) for her register.
6. **Registries** — add the language to `STRINGS_REGISTRY` and `WIZDA_REGISTRY` in `languageStore.ts`. TypeScript's `Record<SupportedLanguage, …>` will demand this as soon as step 1 lands.
7. **Backend display names** — confirm the seed scrapes that language (see `docs/domain.md`); a UI catalog without scraped `name<Lang>` columns gives you translated chrome around English item names.

`generateStaticParams`, the middleware, `hreflang`, and the sitemap all read `OFFERED_LANGUAGES` — they need no edit.

## Adding a route

1. Create it under **`app/[lang]/`**. A route outside that tree has no language and no root layout.
2. Add its path to **`ROUTE_PATHS`** in [`app/pageMetadata.ts`](../packages/web-client/src/app/pageMetadata.ts). The sitemap and the `hreflang` alternates derive from this.
3. Add a **`meta.<route>`** entry — `title` and `description` — to `UiStrings` **and every language catalog**.
4. Export a `generateMetadata` from the page that calls `buildPageMetadata(lang, '<route>')`.
5. Link to it with **`useLocaleHref()`**, never a bare `href="/thing"` — a bare path bounces through the middleware's redirect on every click instead of navigating client-side.
6. If the route needs a "which page am I on" check, compare against **`stripLocale(usePathname())`** so the check stays language-agnostic (see `Shell.tsx`, `WizdaGreeter.tsx`, `DetailProvider.tsx`).

> **Step 3 is the one that gets forgotten.** Metadata is per-language and it is where multilingual SEO actually lives — the slugs are English on purpose, so the localized `<title>`/`<description>` carry the whole weight of a language's search presence. A route with no `meta` entry silently inherits the site default in *both* languages.

## Adding or changing a string

Add it to `strings.en.ts` **and every other `strings.<lang>.ts`**; `strings.test.ts` enforces structural parity and non-empty leaves. Static text is a string; anything interpolated, pluralized, or word-order-sensitive is a function leaf, so the catalog owns the sentence and the caller owns the values. Wizda's lines live in her own parallel catalog, not here.

## Decisions worth not re-litigating

### Why 307, never 301

The language-less redirect is deliberately **temporary**. A 301 is cached by browsers more or less permanently, so a visitor who later switches language would keep being sent to the old one from cache — the middleware would never run again, and the switcher would look broken with nothing in the server logs to explain it. Any redirect whose target varies per visitor has to be temporary. The response also carries `Vary: Accept-Language, Cookie` and `Cache-Control: no-store` so intermediaries don't cache it either.

This costs nothing in search terms: Googlebot sends `Accept-Language: en` and carries no cookie, so it lands deterministically on `/en/…` every time, which consolidates indexing the same way a 301 would have.

### Why the slugs stay English

Only the locale prefix is translated: it's `/ja/equipment`, not `/ja/soubi` or `/ja/装備`. Translated slugs pay off when the slug *is* the search keyword — a blog post, a product page. Wizda's routes are navigation chrome, and what people actually search for is item names, which never appear in the path at all. Against that, per-locale slugs mean a bidirectional mapping table, a path-translating language switcher, and a new slug in every language for every future route — and in Japanese they end up either percent-encoded into noise in every shared link or transliterated into romaji nobody types. The SEO value lives in the localized title and description instead.

### Why the language isn't in React state

`LanguageProvider` holds no state — it takes the route segment as a prop and publishes it. A `useState`/`localStorage` version can only ever apply *after* hydration, which is the flash this design exists to remove. It also writes the module-level mirror during render rather than in an effect, so [`services/api.ts`](../packages/web-client/src/services/api.ts) reads the right language for its very first request; the old version fired every cold-load fetch as `?lang=en` and then refetched.

## Gotchas

- **Never read a catalog at module scope.** `getStrings()`/`getWizda()` resolve against `activeLang`, which starts at `en` and is written by `LanguageProvider` during render — so anything evaluated at *import* time (a `const` outside a function, a hoisted lookup table, a default parameter built from a catalog) captures English permanently and silently stops switching. Call them inside the function that uses them; in components prefer the `useStrings()`/`useWizda()` hooks, which also re-render on a language change. `CategoryFilter.tsx` carries a comment marking one spot where this bites.
- **`middleware.ts` must stay off the catalogs.** It imports only `i18n/locale.ts`, a deliberate leaf module with no string or voice imports — pulling in `languageStore` would drag every language's full text into the middleware bundle.
- **Well-known paths must not get a prefix.** `/sitemap.xml`, `/robots.txt`, `/manifest.webmanifest`, `/sw.js`, `/api/*`, `/umami/*` and anything with a file extension are excluded by the middleware matcher.
- **An unknown prefix 404s via one redirect, not directly.** `/fr/junks` names no *offered* language, so the middleware treats it as language-less and sends it to `/en/fr/junks`, which has no route and 404s. The outcome is right and the alternative — guessing which path segments "look like" a locale — would be worse. Same for `/ko` and `/de`, which the backend scrapes but the frontend doesn't offer.
- **Analytics paths change shape.** Umami now reports `/en/junks` and `/ja/junks` rather than one `/junks`. Pre-split history stays under the old paths.
- **`ORACLE_NAME` ("Junk Oracle") is deliberately untranslated** — it's the tool's name, treated as a proper noun, so it reads the same in both catalogs.
